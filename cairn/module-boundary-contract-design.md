# 模块边界与契约设计（AI 协作冲突规避）

## 背景

团队 vibe coding 修一个功能就改动很多模块 → 冲突频发。根因有三个：共享文件边界模糊、变更波及面大、缺少显式契约。设计以「纵切模块 × 横切数据链路 × 共享底座 + 契约层」组织模块，把冲突从"发散"收敛到"契约评审"。

## 核心结构（两竖夹多横）

- **纵切** = 模块（限界上下文 / 按特性划分）= **拥有权主体**（一人管一个模块，变更收在模块内）
- **横切** = 数据链路（数据在模块间穿行的管道，pipes-and-filters）——**按人看护**（一条完整链路一人负责端到端）
- **共享底座** = 公共模块（被所有模块依赖），抽离成单独一块，**不走横切**；各模块经出口契约调用
- **契约层** = 模块与模块交互处的接口定义薄层（两个竖块之间夹着的多个横块，每个横块 = 一个独立的薄契约）

## 所有权与职责边界（核心）

- 链路（横切，一人看护）：只负责节点之间怎么传——顺序、转换、超时/失败策略、时序、schema 版本。不拥有业务逻辑。
- 模块（纵切）：只负责节点内部做什么——具体业务规则。不拥有"何时被调用、数据如何流转"。
- 共享底座：稳定、少变；改一次全员评审。

## 关键区分：契约 = 定义 / 触点 = 绑定

- **契约（Contract）**：数据长什么样——DTO/schema、接口签名、版本号，可复用声明。
- **触点（Touchpoint）**：模块把自己的内部类型接入契约的适配点（生产侧 模块→DTO、消费侧 DTO→模块，一个契约两侧各一个触点）。
- 触点按模块独立演进（低门槛）；新增链路 = 新增契约（中门槛）；**既有契约本体只按版本演进，不按需重写**（最高门槛）。

## 私有 vs 共享类型（改动策略分叉）

- 判断标准：该类型的生产者/消费者跨不跨链路。
- **私有**（仅一条链路的两个端点）：直接改 + 两端同步；建议类型放链路私有命名空间，不进共享契约。
- **共享**（跨多条链路）：只能版本化演进 + 全消费者评审。
- 注意：注册进传输 ≠ 共享——注册是传输必需，私有/共享决定的是"直接改还是加版本"。

## 改类型「四处辐射」

改一个链路数据类型，联动四处（不只是触点）：① 契约定义 ② 全部触点适配 ③ 链路中段转换 ④ 落盘/外部边界兼容。强类型编译器会把前四处列全（Rust 优势）；弱类型/JSON 边界靠 schema 校验测试兜底。触点转换建议集中成可单测的纯函数，改类型跑往返测试防"生产侧改了消费侧没改"。

## 形态 A：定义层注册表 + 运行时本地分发

- 定义统一一处（schema 单一事实源，各语言从它生成代码）→ 语义一致 + 可观测清单
- 运行时本地分发（每个进程只解析订阅的 key）→ 高频开销小、无中央单点
- 不要形态 B（运行时中央路由进程）：分布拓扑无中央可依赖，且中央进程做厚即上帝模块
- 半公共模块红线：契约层只放定义/版本/schema，**不放业务逻辑**；抽象是为了降变动成本而非显示设计能力（YAGNI——出现第二个真实消费者才提升为共享契约）

## 静态 vs 运行时架构（项目化应用）

教材定义不收录，保留项目化应用一句：**静态架构管"分层与解耦"（依赖方向编译期可查、可测性），运行时架构管"线程与生命周期纪律"（编译能过、跑起来才炸的问题）**。mdor 用它对照：C4 图管静态，序列图 SD-1~4 + M6 真机清单 C/D 项管运行时。

## 对 AI / vibe coding 的价值

- 纵切/横切 = 两个物理分离的代码区 + 一条清晰的指令边界：AI 指令可干净指定"改模块 A 内部"或"改链路第 3 跳"，几乎不互相污染。
- 链路代码是线性顺序描述数据怎么走，AI 理解最好。
- 冲突收敛到最后一步：新增链路/触点 = 多人协作点，由链路 owner 一人牵头串——这是"不能完全避免"的那部分，有明确责任人而非随机爆发。

## 风险与红线

- 半公共模块最易膨胀成上帝层/瓶颈——契约层只放定义。
- 既有契约本体被"按需"改动 = 重新制造最大冲突源——只版本化演进。
- 过度抽象（YAGNI）——不为想象中的未来建抽象层。
